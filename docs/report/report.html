1Overview

The player is the restaurant manager. Every turn they decide what each member of staff does. Staff time is scarce, so the real decision is always who comes first: seat the new arrival, take an order, or serve the dish that is getting cold?

Base setting (always offered)

  • 18 turns, 2 tables, no early ending
  • Waiter, Chef, Cashier: 1 task each per turn
  • Arrivals on turns 1, 4, 7, 10, 13, 16
  • Salad $9 (1 unit), Burger $15 (1), Pasta $18 (2)
  • Win: ≥ 4 paid, ≥ $45, avg satisfaction ≥ 60

Run it

./run.sh              # build and play
./run.sh --script scripts/stage3-victory.txt
./run.sh --plain      # no colour, ASCII
./test.sh             # 22 rule checks
git checkout stage-1  # any stage, then ./run.sh

Windows: run.bat / test.bat. Needs only a JDK (17+); no build tool, no network.

2.1Reading the class diagram

Encapsulation

Money is immutable and stores integer cents, so $9.00 + $15.00 is exactly $24.00 and VIP and Happy Hour discounts round once per step.

Restaurant is the only object that moves a customer between the queue, a table and the door. Table.assign/release and Customer.seatAt/placeOrder/pay/leave are package-private (~), and every collection is returned read-only. The UI cannot put the game into an impossible state even by accident.

Polymorphism

Customer owns the visit life cycle. Subclasses override only three hooks: satisfactionLossPerTurn(), chooseFrom(Menu) and billFor(Money). Game, Waiter and Cashier never ask a customer's type.

MenuItem.price()/prepUnits() are answered differently by Dish and ComboMeal; Order and Chef treat both the same.

Composition and aggregation

◆ Game owns its restaurant, staff, Happy Hour and pricing policy; they live and die with one game. ◆ Restaurant owns its 2 tables and its orders.

◇ Restaurant aggregates customers, who arrive from outside. ◇ A ComboMeal aggregates 2 existing Dishes that also appear on the menu on their own.

Inheritance and interfaces

StaffMember holds the per-turn task budget. DirectedStaff adds the manager-facing template method perform(); Waiter, Chef and Host fill in duties() and carryOut(). Cashier is automatic, so it extends StaffMember only.

PriceModifier is the one interface, implemented by HappyHour.

Layers rush.ui boundary: reads input, draws the screen, no rules · rush.control the turn sequence and setting · rush.staff what each role may do · rush.policy pricing rules · rush.model entities and their invariants. Dependencies point one way: ui → control → staff → policy → model.

Records (Command, ActionResult, TurnContext, Objective, Scoreboard, GameResult, GameEvent) are immutable value carriers; their components are public final by construction.

4.2 Design principles, where the code actually shows them

SRP · Single responsibility

Each rule has exactly one home. "A dish finished this turn cannot be served until next turn" is checked only in Order.serve; the Waiter just calls it, and the UI just shows the RuleViolation message. Dashboard only reads the game and CommandParser only checks the shape of input (seat 2 1), never whether the move is legal. When we changed the end-of-turn layout we touched one class.

OCP · Open for extension, closed for modification

Stage 1 → 2 added VIP and Critic customers with no change to Game, Waiter, Chef, Cashier, Restaurant, Order or Customer: git diff stage-1 stage-2 -- src/rush/control/Game.java src/rush/staff is empty. Stage 3's Host is a new DirectedStaff registered in GameConfig.hireDirectedStaff(); the console's staff loop prompted it without any change to that loop. Combos needed no change to Order, Chef or Waiter.

LSP · Liskov substitution

Subclasses cannot break the life cycle: the transitions (seatAt, placeOrder, pay, leave) are implemented once in Customer, guarded by status checks, and no subclass overrides them. Subclasses only vary the three behaviour hooks, and each override keeps the base contract (a loss rate ≥ 0, an item from the given menu, a bill ≤ the menu price). The test "all customer types follow the same order and service flow" runs a VIP through the exact sequence a Regular uses. A ComboMeal stands in for any MenuItem: the Critic's "most elaborate item" comparator and Chef's unit counting work unchanged.

ISP · Interface segregation

The Cashier takes no instructions, so it is a StaffMember but not a DirectedStaff and is not forced to implement duties(), carryOut() or options(). ConsoleUI depends only on the narrow DirectedStaff API (perform, options, hasTaskLeft). PriceModifier has a single method.

DIP · Dependency inversion (partly)

PricingPolicy depends on the PriceModifier abstraction, not on HappyHour. ArrivalSchedule depends on a CustomerFactory functional interface, so it never names a concrete customer class. The console depends on DirectedStaff, not on Waiter. Honest limit: Game still constructs HappyHour and PricingPolicy itself. Injecting them through GameConfig would be the next step if more policies appeared.

4.5 An alternative design we considered: the State pattern for customers

Customers move through WAITING → SEATED → ORDERED → EATING → READY_TO_PAY → PAID (or LEFT). We sketched a State pattern: one class per state (Waiting, Seated, …), each implementing seat(), order(), serve(), endOfTurn() and rejecting what it does not allow.

For Every transition and its legality is in one place per state; illegal moves fail by design.
Against (why we chose the enum) The life cycle is strictly linear, and the type behaviours (loss rate, bill, food choice) cut across all states, which would mean seven state classes times three customer types to reason about. An enum with guarded transition methods in one abstract class is shorter, easy to test, and keeps the polymorphism where the brief asks for it: in the customer types.

Also rejected: a CustomerType enum with switch statements in the controller (contradicts "dispatch through the customer objects"), and a Decorator chain for prices (the discount order "VIP first, then Happy Hour" reads more clearly as an explicit list in PricingPolicy).

8Rule interpretations we documented

TopicWhat the game does
Food choice (all stages)Deterministic rotation: guest #n orders item n on the menu board, wrapping around. Shown when the order is taken.
Critic's special behaviourOrder preference: always the item with the most preparation units, the dearer one on a tie (Pasta in Stage 2, Salad + Pasta Combo in Stage 3). Cosmetic 1–5 star review on payment (no effect on scoring).
Combo choice ruleCombos follow the dishes on the board, so the rotation gives guests #4 and #5 the two combos.
Combos on the menuSalad + Burger ($21.60, 2 units), Salad + Pasta ($24.30, 3 units).
Display orderThe scheduled arrival (step 1) is processed, then the start-of-turn dashboard is drawn, so the manager sees the new customer before choosing.
Host and Waiter orderHost, then Waiter, then Chef. The Waiter may take the order of a customer the Host seated this turn (consistent with the Chef working on an order the Waiter took this turn).
Happy Hour startOffered at the start of each turn until used, before any staff member acts. Recovery is applied immediately on the first turn and at the start of the second.
"Waiting for a table or food"WAITING, SEATED (not yet ordered) and ORDERED (including a READY but unserved dish). The same set loses satisfaction at turn end.
RoundingHalf-up to the nearest cent after each percentage step: VIP Burger in Happy Hour $15.00 → $13.50 → $10.80.
Seatingseat 2 uses the first free table; seat 2 1 names one.
Auto-wait (Stage 3)A staff member whose only possible action is wait waits without a prompt.
Satisfaction displayA paid customer's satisfaction is frozen when they pay, so the average equals the values recorded at payment.

9Reflection

What worked

  • Designing from the published brief. Because all three stages were known up front, Stage 1 already separated the customer life cycle from customer behaviour. Stage 2 then touched only configuration, one value-object helper and presentation.
  • Rules as exceptions with reasons. Putting each rule in the object that owns the data (Order.serve, Table.assign, HappyHour.activate) gave us clear error messages for free and kept the UI free of rules.
  • Scripts as tests. Recording runs as plain command files made every victory and defeat reproducible for the TA, the video and the automated checks alike.

What we would do differently

  • Inject PricingPolicy and its modifiers through GameConfig instead of building them in Game, so a new policy needs only registration.
  • Use structured event objects instead of English strings, which would let tests assert on events rather than text.
  • Write the strategy-replay tool (§5) as part of the test suite earlier: it found a balance issue (the Host changes the best Waiter priority) that we only noticed late.
