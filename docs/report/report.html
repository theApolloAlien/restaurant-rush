1Overview

In Restaurant Rush the player is the restaurant manager. Each turn they tell the Host, Waiter and Chef what to do, and the Cashier collects payment automatically. With one of each and only two tables, there is never enough staff time, so every turn comes down to the same question: who do we look after first?

Base setting

  • 18 turns, 2 tables, no early ending
  • Waiter, Chef and Cashier, one task each per turn (Stage 3 adds a Host)
  • One arrival on turns 1, 4, 7, 10, 13 and 16
  • Salad $9 (1 unit), Burger $15 (1), Pasta $18 (2)
  • Win: at least 4 paid, $45 revenue and an average satisfaction of 60

Running it

./run.sh              # build and play
./run.sh --script scripts/stage3-victory.txt
./run.sh --plain      # no colour, ASCII only
./test.sh             # 22 rule checks
git checkout stage-1  # then ./build.sh

After checking out a tag, run ./build.sh before ./run.sh, because the jar is not tracked by git. On Windows, run.bat and test.bat always recompile. Only a JDK is needed, with no build tool and no network access.

2.1 Reading the class diagram

Encapsulation

Money is immutable and stores integer cents, so prices add up exactly and each discount is rounded once. Restaurant is the only class that moves a customer between the queue, a table and the door: Customer.seatAt, placeOrder, startEating, pay and leave, and Table.assign and release, are package-private (~). The few public methods that change state (finishEating, loseSatisfaction, recover, Order.prepareUnit and serve) check the current status first. Every list is handed out read-only, and the UI only gives commands to Game.

Polymorphism

Customer owns the visit life cycle. The subclasses only override satisfactionLossPerTurn(), chooseFrom(Menu), billFor(Money) and remarkOnPaying(), plus the type() label, and Game, Waiter and Cashier never check a customer's type. In the same way, Dish and ComboMeal answer price() and prepUnits() differently, while Order and Chef treat them the same.

Composition and aggregation

Game owns its restaurant, staff, Happy Hour and pricing policy, which exist only for one game. Restaurant owns its two tables and its orders. Customers arrive from outside, so Restaurant only aggregates them. A ComboMeal aggregates two Dish objects that are also on the menu by themselves.

Inheritance

StaffMember holds the per-turn task budget. DirectedStaff adds the template method perform(), and Waiter, Chef and Host fill in duties() and carryOut(). The Cashier takes no instructions, so it extends StaffMember directly. HappyHour implements the PriceModifier interface.

The packages form layers, and dependencies only point one way: ui reads input and draws the screen, control runs the turn sequence, staff decides what each role may do, policy holds the pricing rules, and model holds the entities and their rules. The small records (Command, ActionResult, TurnContext, Objective, Scoreboard, GameResult, GameEvent) are immutable value objects.

4.2 Design principles in the code

Single responsibility. Each rule lives in one place. "A dish finished this turn is served next turn at the earliest" is only checked in Order.serve. The Waiter just calls it, and the UI just prints the RuleViolation message. CommandParser only checks that seat 2 1 is well formed, never whether the move is legal, and Dashboard only reads the game.

Open/closed. Going from Stage 1 to Stage 2 added the VIP and Critic without touching Game, Customer, Restaurant, Order or any staff class (git diff stage-1 stage-2 -- src/rush/control/Game.java src/rush/staff is empty). In Stage 3 the Host is a new DirectedStaff registered in GameConfig, and the console's loop over game.directedStaff() picks it up unchanged (ConsoleUI changed only for the Happy Hour prompt and auto-wait, see Section 6). Combos needed no change to Order, Chef or Waiter.

Liskov substitution. The status transitions (seatAt, placeOrder, pay, leave) are written once in Customer and no subclass overrides them. The overrides keep the base contract: a loss rate of at least 0, an item from the given menu, and a bill no higher than the menu price. A rule check runs a VIP through exactly the same flow as a Regular. A ComboMeal can stand in for any MenuItem, and the Critic's choice and the Chef's unit counting work unchanged.

Interface segregation. The Cashier takes no instructions, so it is a StaffMember but not a DirectedStaff, and it does not have to implement duties() or carryOut(). ConsoleUI only uses the small DirectedStaff API, and PriceModifier has a single method.

Dependency inversion (partly). PricingPolicy depends on PriceModifier rather than HappyHour, and ArrivalSchedule depends on a CustomerFactory interface, so it never names a concrete customer class. However, Game still creates HappyHour and PricingPolicy itself. Passing them in through GameConfig would be the next step if more policies were added.

4.3 Patterns we used

PatternWhereWhy
Template methodDirectedStaff.performThe task-budget check, the duty check and "a rejected move costs nothing" are written once for every role.
Composite (one level)MenuItem, Dish, ComboMealA combo is a menu item built from two Dish leaves, so its price and units are derived rather than copied. A combo cannot contain another combo.

4.5 An alternative we considered: the State pattern for customers

A customer moves through WAITING → SEATED → ORDERED → EATING → READY_TO_PAY → PAID, or LEFT. We sketched one class per state, each implementing seat(), order(), serve() and endOfTurn() and rejecting moves it does not allow. That puts every transition in one place per state. We kept the enum because the life cycle is strictly linear, and the type behaviours (loss rate, bill, food choice) cut across every state. We would have had seven state classes and three customer types to keep in sync. An enum with guarded methods in one abstract class is shorter, easy to test, and keeps the polymorphism in the customer types, where the brief asks for it.

We also rejected a CustomerType enum with switches in the controller, because the brief asks for dispatch through the customer objects. We also rejected a Decorator chain for prices, because "VIP first, then Happy Hour" reads more clearly as an ordered list in PricingPolicy.

Three things stand out:

  • Serve before you seat. A served customer stops losing satisfaction and frees the table two turns later. Seating first only moves the waiting from the queue to a table.
  • The Host changes the best priority. Once the Host does the seating, taking orders first beats serving first (5 paid against 4). Using the Host alone turns the weakest strategy from a defeat into a victory.
  • Happy Hour is a trade-off. On turn 7 it costs $3.24 in revenue but lifts the average from 75.6 to 82.6. On turn 14 it helps nobody who can still pay before the game ends.

8Rule interpretations

Where the brief left a choice to us, this is what the game does.

TopicWhat the game does
Food choiceA fixed rotation: guest #n orders item n on the menu, wrapping around. The choice is shown when the order is taken.
The Critic's behaviourAlways orders the item with the most preparation units, and the more expensive one on a tie (Pasta in Stage 2, the Salad + Pasta Combo in Stage 3). Leaves a 1 to 5 star review on paying, which does not affect the score.
Combo choiceCombos come after the dishes on the menu, so the rotation gives guests #4 and #5 the two combos.
Combos on the menuSalad + Burger ($21.60, 2 units) and Salad + Pasta ($24.30, 3 units).
Display orderThe scheduled arrival (step 1) happens before the dashboard is drawn, so the manager sees the new customer before choosing.
Host and Waiter orderHost, then Waiter, then Chef. The Waiter may take the order of a customer the Host seated this turn, just as the Chef may cook an order the Waiter took this turn.
Starting Happy HourOffered at the start of each turn until used, before any staff member acts. Recovery applies straight away on the first turn and at the start of the second.
"Waiting for a table or food"WAITING, SEATED (not yet ordered) and ORDERED (including a READY dish not yet served). The same group loses satisfaction at the end of the turn.
RoundingHalf-up to the nearest cent after each percentage: a VIP Burger in Happy Hour goes $15.00, $13.50, $10.80.
Seatingseat 2 uses the first free table; seat 2 1 names the table.
Auto-wait (Stage 3)A staff member whose only possible action is wait waits without a prompt.
Recorded satisfactionA customer's satisfaction is frozen when they pay, so the average uses the values at payment.

9Reflection and contributions

What worked

  • Planning for all three stages from the start. Since every stage was published up front, Stage 1 already kept the customer life cycle separate from customer behaviour. Stage 2 then only touched the configuration, one helper in Money, and the display.
  • Rules that explain themselves. Putting each rule in the object that owns the data (Order.serve, Table.assign, HappyHour.activate) gave us clear error messages for free and kept the UI free of rules.
  • Scripts as tests. Saving runs as plain lists of commands made every victory and defeat reproducible for the marker, the video and the rule checks.

What we would do differently

  • Pass PricingPolicy and its modifiers in through GameConfig instead of creating them in Game, so a new policy only needs registering.
  • Use structured event objects instead of English strings, so tests can check events instead of text.
  • Build the strategy replays from Section 5 into the test suite earlier. They showed that the Host changes the best Waiter priority, which we only noticed late.
